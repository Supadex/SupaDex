# Runbook: governance roles, delays, cancellation (ADR-0010)

Status: draft for review. PRODUCTION READINESS NOT ESTABLISHED.

- **Delay floor:** `SupaTimelock.delayFloor` is immutable. It is 48 h on every chain except the listed local and test chains (1 h there). Neither the constructor nor `updateDelay` accepts less. Unknown chains get 48 h (fail-safe). The verifier also requires `minDelay ≥ 48 h` on value-bearing profiles. Note: Edith 10-A proposed a constructor parameter. This implementation derives the floor from chain id instead, so a deployer cannot pass a short floor. To review: whether the test-chain list is acceptable.
- **Role holders:** on value-bearing profiles, PROPOSER, EXECUTOR, CANCELLER, GUARDIAN and OPERATOR must be Safe-style multisigs. The verifier checks code, `getThreshold() ≥ 2` and `getOwners().length ≥ threshold`, and requires GUARDIAN ≠ PROPOSER. Including OPERATOR in this check is a strict reading of "every role holder" and can be relaxed if Edith prefers.
- **Canceller veto / liveness risk (10-D):** a canceller can cancel every queued operation indefinitely. That is a liveness veto by design, because cancellation is the defence against a malicious proposal. If the canceller set is compromised or uncooperative, governance cannot make progress. Last-holder protection means a canceller cannot be removed without a timelocked op, which the canceller can itself cancel. **Recovery is a redeploy**: deploy a fresh stack, then pause the old vault through the guardian (exits stay open) and migrate liquidity. Mitigations: keep the canceller a high-threshold Safe whose signers differ from the proposer's, and monitor `CallCancelled`.
- **Ownership transfers** are single-step (owner = timelock). A 2-step transfer (10-E) is not implemented. It is low priority because the transfer itself is a timelocked op.
- **Salt recovery:** `schedule` emits `CallSalt(id, salt)` next to `CallQueued`, so Safe-wrapped schedules can be executed from logs alone. `isOperationExpired(id)` distinguishes expired from never-scheduled.
- **Delay-floor allowlist (ADR-0010, remediation-4):** the test-chain list is the shared `contract/libraries/ChainIds.sol` (`isLocal` = 31337 only; `isTestnet` = Sepolia, Holesky, Hoodi, Base Sepolia, Arbitrum Sepolia, OP Sepolia, Polygon Amoy, BNB testnet). `SupaTimelock.isTestChain` and `DeployEnvironment.classify` both read it; `test/unit/ChainIds.t.sol` asserts they agree. Monad testnet 10143 and geth-dev 1337 are not on it, so they get the 48 h floor and deploys there are blocked.
- **BIN curve:** it is paused at genesis on value-bearing networks (`CircuitBreaker.pauseCurve(1)`) and the verifier checks this. Unpausing is a timelocked op that requires Jexi's sign-off and an external audit.

## Plugin whitelist policy: delta-returning plugins (APUS-SUPADEX-024)
- `setPluginCanReturnDelta(plugin, true)` lets a plugin reduce an LP's removal credit (a principal haircut) or confiscate unvested fees.
- Since remediation-3, the PoolManager redistributes the retained principal like confiscated fees. It is donated to in-range LPs, or booked as protocol fees when the pool has no active liquidity. It is never stranded in `reservesOf`. The plugin itself receives nothing.
- Whitelisting a principal-haircutting plugin is still a governance decision that changes LP economics. It needs its own security review. The shipped LVR plugin may not return deltas; AntiJIT returns fee deltas only.

## Stable pools at launch: canonical pools created by the team (ADR-0007, Edith R3.4-1)
- Pool keys are unique per (pair, fee, plugin), so the first creator of a key fixes its initial A (within the governance range [minA, maxA]). A griefer could create the canonical USDC/USDT key with a poor A. The impact is efficiency only (no principal at risk), but it degrades the default route.
- **Launch procedure:** before (or in the same window as) any public announcement on a network, the team creates every canonical stable pool (each near-1:1 pair × each fee tier the UI lists) through the reviewed deploy flow with the reviewed A, and records the pool ids in the deployment record. The UI's default stable route points only at these recorded pool ids.
- If a key was front-run with a poor A: governance ramps it via the timelock (≤ 10× per ramp, ≥ 1 day per ramp, guardian may stop a ramp), or the UI routes to another fee tier. Do not delist silently; show the pool's A.
- Only near-1:1 pegged pairs (after decimal normalisation) are eligible. Never create stable pools for yield-bearing, rebasing or rate-drifting assets (wstETH/ETH, rETH, stETH, sDAI): the engine has no rate provider and always starts at the 1:1 peg.
